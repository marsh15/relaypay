# RelayPay v2.0.0-m16: payment model, fees and GST, and the harness findings fixed

M16 makes every bug the M15 proof harness found impossible, and extends the payment model.
v2.0 now covers a persisted state machine, partial capture, expiry, void, and platform fees with
GST, and exposes them under `/api/v2`. `/api/v1` bytes, idempotency replay and every existing
journal are unchanged; `make api-contract` proves the frozen v1 surface on every commit.

## Harness findings fixed (found by M15)

| ID | Was | Now | Commit |
|---|---|---|---|
| F1 | A refund drew on raw AVAILABLE and could spend funds reserved for an in-flight payout; AVAILABLE reached −100000 paise | Refunds take only `available − reserved`; the rest is a receivable. Migration 0020 adds a deferred trigger that rejects any reservation or AVAILABLE debit that would overdraw, as a database backstop | `419ab3f`, `5cd01a4` |
| F2 | A payout whose worker died after the bank paid stayed SENT forever, funds reserved | SENT attempts past a grace period get lookup-only bank recovery; the transfer is never re-sent | `a619b17` |
| F3 | An operation committed but never dispatched was never recovered | The poller first-sends it through `prepare_first_send`, race-safe with the API's own late dispatch | `a619b17` |
| F4 | A crash before the provider call always ended in manual review | A signed, identity-bound "not found" past `PROVIDER_NOT_FOUND_GRACE_SECONDS` fails the operation ([ADR-011](../adr/011-signed-not-found-is-proof-of-absence.md)) | `f3e7a13` |

The chaos harness now treats F2–F4 as hard failures; `make chaos` reports zero findings.

## Payment model

- **Persisted state machine.** `payment_intents.status` is one of `created`, `requires_action`,
  `authorised`, `captured`, `partially_refunded`, `refunded`, `failed`, `expired` or `cancelled`.
  It has one writer and an immutable history, and a database trigger rejects illegal
  transitions. Migration 0019 backfilled existing payments.
- **Partial capture (D6).** There is one capture per payment, of up to the authorized amount; the
  rest is released.
- **Authorization expiry.** Holds last `AUTH_HOLD_SECONDS` (7 days), or a per-request
  `hold_seconds` on v2. The database derives `expires_at`. A poller task expires uncaptured
  payments, and capture refuses a lapsed hold under the payment lock.
- **Void.** A `VOID` provider operation releases an authorised, uncaptured hold. It reuses
  send-before-HTTP, lookup-only recovery and idempotent replay. Void and capture exclude each
  other.
- **Fees and GST (D7).** A versioned per-merchant fee schedule splits each capture at initiation
  into the platform fee, GST on the fee, and the merchant's net. The capture journal credits
  PLATFORM_FEE_REVENUE (a new INCOME account type) and GST_PAYABLE. Settlement, refund sourcing
  and forecasts use the net. Refunds use the RETAIN policy. The fee calculator itself is
  hand-written by the maintainer and is pending (see [PROVENANCE.md](../../PROVENANCE.md)).
- **`/api/v2`.** A status view, authorize with a hold, partial capture, and void; see the
  [HTTP API reference](../api/reference.md#apiv2-v20). The SDK facade wraps all four.

## Found and fixed while building M16

- **Postings were sequentially scanned on every balance read and every ledger write.**
  Balance sums filtered on `account_id`, but the only index led with `organisation_id`. The 0001
  journal-balance trigger looked up postings by `journal_id`, which had no index at all. Migration
  0021 adds two covering indexes, making both index-only scans. The account sum went from
  3.5–6.2 ms to 0.39 ms at 27k postings, and a 3 × 1,000 chaos slice from 237 s to 73 s.
- **CI had been red since T16.1.** The tests passed, but the merchant-balance demo, which runs on
  the same database afterwards, crashed. The cause was a global recovery batch hitting a test
  fixture, which exposed a real bug: one failing unsent operation aborted the whole poller sweep.
  Each operation is now contained, and the demo recovers only its own tenant (`22b634a`).
- **A load-sensitive test assumption.** Duplicates of an in-flight capture correctly return 202,
  not 200 (`f0d732a`).
- **Two near-regressions caught before commit.** The Hypothesis state machine caught capture
  checks that would have changed v1 retry convergence. The full suite caught that "succeeded
  implies an expiry" must be derived by the database, not by each writer.

## Verification

Each stage was verified before its commit:

- lint, format, strict mypy, `alembic check` on both trees;
- the frozen `/api/v1` contract and SDK drift;
- the full suite in CI order (495 tests at the end of M16), followed by the merchant-balance demo
  on the same database;
- the evaluation gate and a chaos sweep;
- for every fix, its test was shown to fail with the fix removed.

`scripts/verify_m16_upgrade.py` seeds payments in every lifecycle state at head, steps back to
0018, and proves migrations 0019–0025: backfills are correct, evidence checksums are unchanged,
and downgrade and re-upgrade are clean. CI runs it in `release-gate`.

Measured locally (Apple M1, Postgres capped at 4 CPU): full suite 495 passed in about 6 minutes;
chaos 3 × 1,000 operations in about 40–75 s, zero harness failures.
