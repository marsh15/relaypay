# RelayPay v2.0.0-m15: proof harness

M15 is the first milestone of v2.0 ("never loses a paisa", plan:
[docs/plans/v2.0-never-loses-a-paisa.md](../plans/v2.0-never-loses-a-paisa.md)). It adds the
machinery that tries to make RelayPay create, lose or move money twice, and runs it against the
v1.0.1 code. The only production change is twelve one-line crash-point hooks (inert unless chaos
injection is configured, and refused when `APP_ENV=production`) plus migration 0018. `/api/v1`,
idempotency replay bytes and every existing journal are unchanged.

## What was added

- **Shared proof foundation** (`tests/support/`): an isolated tenant per test or seed, a signed
  thread-safe fake provider with scripted outcomes, and exactly-once counters per stable key.
  Hypothesis is a dev dependency, with derandomized `ci` and 500-example `nightly` profiles.
- **Hypothesis state machine** (`test_stateful_payments.py`): drives create, authorize, capture,
  refund, replay, key reuse, recovery and pending resolution. Lost, declined and pending provider
  outcomes are injected. Money facts are checked after every step.
- **Refund properties** (`test_property_refunds.py`): random partial-refund lists, applied
  sequentially and from 8 concurrent workers. Accepted refunds never exceed captured.
- **Contention proofs:** a 500-way payout race against a balance that fits exactly 250 (the
  production path reserves exactly 250, with 0 errors). 50 concurrent identical HTTP requests
  through a real server produce one payment and byte-identical bodies, and a capture produces
  exactly one provider mutation.
- **System snapshot** (`relaypay.proof.capture_snapshot`) and the contract for the maintainer's
  invariant checker. That checker is hand-written (see [PROVENANCE.md](../../PROVENANCE.md));
  55 red specification tests are waiting for it.
- **Chaos harness** (`scripts/chaos`, `make chaos`): seeded operation schedules with crash points,
  lost responses, declines, pending effects, replays and concurrent duplicates. Each run ends
  with quiesce, then snapshot, then the invariant check. Full mode (`make chaos-full`) drives the
  real stack over HTTP with SIGKILLs and a Postgres restart; it is manual-only in CI.
- **Migration 0018:** database-enforced immutability for 24 tables from migrations 0012–0017.
  17 get full-row triggers and 7 get column-scoped triggers. The 15 genuinely mutable workflow
  tables are listed with their reasons.
- **Locking strategy interface** for the M19 payout-locking comparison. The three strategies are
  hand-written stubs; the legacy production path is the control.
- **CI:** new `proof-gate` job (proofs and the 20×1000 chaos sweep, with Postgres raised to 4 CPU
  and 700 connections), `handwritten-gate` job (red until the maintainer's modules exist), and a
  manual `chaos-full` dispatch. `release-gate` no longer runs these tests twice.

## Measured (local: Apple M1, 8 cores; Postgres container capped at 4 CPU via compose.proof.yaml)

- `make chaos`: 20 seeds × 1,000 ops = 20,000 operations, 884 injected crashes and 1,516
  provider faults, zero harness failures, about 300 s. Invariants: **not evaluated** until the
  hand-written checker lands. The harness never reports "0 violations" without it.
- Hypothesis `ci` profile, stateful and property files: about 50 s on an idle database.
- Full suite excluding `handwritten`: 317 passed, 1 strict xfail (F1), 12m38s locally (includes the proof and chaos tests that CI runs in `proof-gate`).

## Bugs found by the harness (production code not yet changed)

| ID | Finding | Effect | Fix |
|---|---|---|---|
| F1 | A refund draws on raw AVAILABLE and ignores payout reservations | Settle 100000, reserve a 100000 payout, refund in full, then finalize the payout: AVAILABLE = −100000 paise. The customer is refunded and the merchant is paid the same money. `derive_balances` hides it by clamping `payout_eligible` at 0 | M16 T16.4. Strict xfail `test_f1_refund_vs_reserved_payout.py` |
| F2 | `run_payout_batch` selects only PREPARED and AMBIGUOUS attempts | A worker that dies after the bank pays but before recording the response leaves the payout PROCESSING with attempt SENT forever, and its funds stay reserved (30 occurrences in 20×1000) | M16 |
| F3 | `claim_due_operations` requires `last_sent_at` | An operation the API committed but never dispatched (API process died after commit) is never recovered unless the client retries with the same key (104 occurrences) | M16 |
| F4 | Crash between "SENT committed" and the HTTP mutation | The provider never saw the request, lookups return 404, and the operation ends in REQUIRES_REVIEW, which `retry_lookup` cannot clear. The same applies to payouts, where `create_retry` accepts only FAILED (130 occurrences). It is conservative and safe (no money moves), but it needs a human every time | Policy decision in M16: treat "not found after a grace period" as a definitive FAILED |

The chaos summary reports F2–F4 as `findings (not failures)` so the sweep stays green while they
are open. Each becomes a failure when its fix lands.
