# RelayPay v0.4.0 — Ledger-backed merchant balances

RelayPay v0.4.0 adds merchant accounts, posting-derived balances, deterministic settlement, and
refund receivables while preserving the v0.1 lost-response contract and existing `/api/v1`
payment response bytes.

> **Synthetic data only.** This release is not a payment processor and must never receive real
> card, bank-account, identity, customer, or other regulated data. It is not deployed or hosted.

## Added in this release

- Multiple merchant accounts within an environment, with one deterministic active default.
  Existing payment creation assigns the default without changing its request or response shape.
- Merchant-scoped pending payable, available payable, payout-clearing, and receivable accounts.
- A deterministic opening journal that transfers each positive legacy merchant-payable position
  into the default merchant's pending balance without rewriting historical journals or postings.
- Capture accounting that credits pending payable and immutable balance transactions keyed to
  their originating journal.
- Organisation-admin merchant-account, balance, balance-transaction, and settlement APIs,
  protected by session authentication and CSRF.
- Route-aware settlement idempotency with exact terminal replay and immutable capture line items.
- Refund funding from payment-attributable pending value, then available value, then receivable.
  Later settlements offset receivables before increasing available balance.
- Posting-derived pending, available, receivable, reserved, and payout-eligible views.

## Compatibility and migration

M3 adds ownership and accounting evidence but does not change `/api/v1` payment wire contracts.
Historical journal, posting, and event bytes remain unchanged. Existing payments are assigned to
their environment's default merchant, and only the net positive legacy payable is moved through a
new balanced opening journal.

Read the [v0.4.0 migration guide](https://github.com/marsh15/relaypay/blob/v0.4.0/docs/migrations/v0.4.0.md).
CI proves both an empty installation and a representative v0.3 upgrade in a disposable schema.

## Runnable synthetic proof

With PostgreSQL migrated and the local mock databases available:

```bash
make merchant-balance-demo
```

The command first runs the permanent lost-response proof and then settles its successful capture.
It prints synthetic identifiers and measured pending, available, receivable, provider-effect, and
evidence counts.

## Known limitations

- INR is the only financial currency.
- Active payout reservations are structurally anticipated but remain zero until the M4 payout
  model is introduced.
- Settlement is synchronous and claims all currently eligible captures for one merchant.
- Merchant balances and settlement are API-first; the expanded operations console arrives in M8.
- A downgrade after M3 financial activity requires restoring the pre-upgrade backup. Disposable
  empty-schema downgrade validation is not a substitute for financial-history reversal.
- No real money, banking data, PCI claim, production SLO, deployment, hosting, or owner-account
  work is included.
