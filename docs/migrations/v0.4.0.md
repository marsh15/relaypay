# Migrating RelayPay v0.3.0 to v0.4.0

RelayPay v0.4.0 adds merchant ownership, posting-derived balances, deterministic settlement, and
immutable balance projections. Migration `0009_merchant_balances` is deterministic and performs
no network I/O.

> **Synthetic data only.** RelayPay is not a payment processor. Back up PostgreSQL before any
> production-style exercise and never use this procedure with real financial data.

## Before upgrading

1. Stop API, worker, poller, and mock processes that can write RelayPay data.
2. Back up the RelayPay database and record its Alembic revision. A direct v0.3.0 upgrade starts
   at `0008_statement_currency`.
3. Retain existing session, CSRF, API-key, idempotency, provider-signing, webhook, and encryption
   secrets.
4. Run the previous-release fixture proof in a disposable schema:

   ```bash
   uv run python -m scripts.verify_m3_upgrade
   ```

## Apply and verify

```bash
uv run alembic -c migrations/relaypay/alembic.ini upgrade head
uv run alembic -c migrations/provider/alembic.ini upgrade head
uv run alembic -c migrations/receiver/alembic.ini upgrade head
uv run alembic -c migrations/relaypay/alembic.ini check
uv run alembic -c migrations/provider/alembic.ini check
uv run alembic -c migrations/receiver/alembic.ini check
```

The RelayPay migration:

- creates one active default merchant for every existing environment;
- assigns all existing payments to that environment-local merchant;
- creates four merchant-scoped INR ledger templates;
- preserves every old journal, posting, and event byte;
- posts one balanced opening journal where the legacy merchant payable is positive;
- creates settlement and immutable balance-transaction evidence tables; and
- provisions the same default account and templates when a future environment is inserted.

After upgrading, run:

```bash
make merchant-balance-demo
```

Confirm the output reports one provider effect, one capture journal, a balanced ledger, pending
reduced to zero, and the captured value available after settlement.

## Operational and rollback notes

- PostgreSQL postings are authoritative. Balance transactions are immutable query projections,
  not mutable balance truth.
- Settlement locks the merchant account and eligible capture rows. Repeating or racing commands
  cannot settle one capture twice.
- Refund validity remains payment-scoped; insufficient merchant funds create receivable rather
  than invalidating an otherwise eligible refund.
- No network call occurs while settlement, refund accounting, or balance evidence is committing.
- Restore the v0.3 backup to roll back after M3 financial activity. The Alembic downgrade exists
  only for disposable schemas without M3 settlement/capture/refund activity.
