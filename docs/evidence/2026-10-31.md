## HTTP measurements

The mixed k6 workload ran for 30 seconds with four virtual users and 100 ms think time. It
created a fresh payment per iteration, authorized and captured it, and refunded roughly half.
All prerequisite calls are included in the HTTP metrics. It completed **191 journeys and
668 HTTP requests**, with no failed journey or HTTP request.

- HTTP latency: p50 **132.908 ms**, p95 **371.412 ms**, p99 **532.648 ms**.
- Observed HTTP throughput: **21.878 requests/s**; completed journeys: **6.256/s**.
- Host: Apple M1, eight logical CPUs, 8 GiB RAM, macOS 27 arm64.
- PostgreSQL 17.6; 100 connections, 128 MiB shared buffers, 4 MiB work memory.
- One API process and one poller; default pool size 5 plus 10 overflow per engine. Compose
  limits each of these services, including PostgreSQL, to one CPU and 512 MiB RAM.
- Dataset before the run: 1,676 payments, 3,853 operations and 5,847 postings, including
  earlier synthetic test history. Docker VM limits and time-series resource consumption were
  not captured; host RAM is not a measurement of memory allocated to Docker.

The fresh load run followed completion of the memory and CI workloads. The poller and normal
simulators remained active. The machine file records `gitDirty: true`: documentation/evidence
and the preserved user edit to `scripts/portfolio_demo.py` were uncommitted; the measured runtime
code was committed. The limiter label is `off`; the kit does not implement a rate limiter.

[Full k6 summary](2026-10-31/load-summary.json) contains command-specific distributions and
