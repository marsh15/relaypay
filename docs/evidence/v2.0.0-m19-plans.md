# v2.0.0 M19 evidence: money-path query plans at one million postings

Synthetic data on one development machine; one warm run per plan. Raw result:
[v2.0.0/money-path-plans.json](v2.0.0/money-path-plans.json). Command:

```bash
uv run python -m scripts.capture_money_path_plans --postings 1000000 \
  --output docs/evidence/v2.0.0/money-path-plans.json
```

The tenant holds 1,000,000 postings, 500,000 journals, 200,000 payments, captures and idempotency
records, 20,000 refunds and 2,000 operations waiting on a lookup. Two ledger accounts carry 98% of
the postings (a hot merchant); a second pair holds 2% (a typical one). Each plan is recorded
freshly loaded and again after `VACUUM`.

| Query (where it runs) | After VACUUM | Plan |
| --- | ---: | --- |
| Payment row lock (`_locked_payment`, every payment command) | 0.03 ms | index scan on `public_id` |
| Idempotency lookup (every command) | 0.01 ms | `idempotency_records_scope_digest_key` |
| Refund trigger: capture lookup | 0.01 ms | `captures_organisation_id_id_key` |
| Refund trigger: reserved sum | 0.02 ms | `ix_refunds_payment_status` |
| Recovery claim (poller, each pass) | 0.09 ms | `ix_provider_operations_recovery` |
| Payments list, first page | 0.04 ms | `ix_payment_intents_scope_created_id` |
| Payments list, deep page with status filter | 0.05 ms | same |
| GCRA admit (every API-key request) | 0.08 ms | primary-key upsert |
| **Balance read, hot account (98% of postings)** | **0.15 ms** | **primary key of `ledger_account_balances`, 3 buffers** |
| Balance read, typical account (2% of postings) | 0.03 ms | same |
| Ledger `SUM`, hot account (`recompute_balance`, verification only) | 105 ms | index-only scan, `ix_postings_account_balance`, 2,776 buffers |
| Ledger `SUM`, typical account | 2.0 ms | same |

Freshly loaded (before `VACUUM`) the hot-account `SUM` is a 290 ms sequential scan; the stored read
is 0.02 ms.

## The finding, and the fix

The first recording of this table (2026-11-19, commit `496a6d9`) had every plan an index plan
except one: the balance `SUM` for an account that holds nearly all of the ledger's postings, a
320 ms sequential scan after `VACUUM`. `derive_balances` ran it three times per call, so a payout,
a settlement or a balance read for such a merchant cost about a second at this size, growing
linearly with postings.

Migration 0035 ([ADR-014](../adr/014-trigger-maintained-account-balances.md)) fixed it. A
database trigger adds each posting to its merchant account's row in `ledger_account_balances` in
the posting's own statement, and `derive_balances` reads that row by primary key: three buffers
whatever the account's size. The ledger `SUM` is still recorded as `balance_recompute_*`. It is
what the stored totals are checked against (money invariant 16, `relaypay_ledger_balance_drift()`),
and what platform accounts, which have no stored row, still use. On this run the planner chose an
index-only scan for it after `VACUUM` (105 ms) where the first recording chose a sequential scan
(320 ms). Both are linear in the account's postings; neither is on a merchant money path now.

The bulk load bypasses triggers (`session_replication_role = replica`), so the script rebuilds the
seeded accounts' stored rows from their postings and asserts `relaypay_ledger_balance_drift()` is
empty for the tenant before it measures.

## What it costs on the write side

The trigger holds the account's stored-row lock from the posting until the transaction commits,
so concurrent postings to one merchant account now run one at a time from the posting on.
`scripts/bench_contended_postings.py` measured it
([raw](v2.0.0/contended-postings-bench.json)): each transaction inserts one capture-shaped journal
(Dr provider clearing, Cr the merchant's pending payable) and commits; `hold` is time spent in the
transaction after the posting, standing in for the rest of a capture's finalization.

| Transactions per second, 16 threads | Before 0035 | After 0035 |
| --- | ---: | ---: |
| One merchant account, hold 0 ms | 1,099 | 590 |
| One merchant account, hold 2 ms | 961 | 182 |
| One merchant per thread (control), hold 0 ms | 936 | 975 |
| One merchant per thread (control), hold 2 ms | 1,030 | 912 |

A single thread is unchanged (370 vs 362 per second at hold 0). Concurrent captures for one
merchant are capped near 1 / (time from the posting to commit); different merchants do not
contend. Platform accounts (provider clearing, fee, GST), which every capture posts to, have no
stored row for exactly this reason. Payout reservation is unaffected (it posts nothing); a 60-way
run of `scripts.bench_payout_locking` was correct for all four strategies with 0 deadlocks.

## Caveats

- One machine, Postgres in Docker with 512 MiB of memory and 128 MB `shared_buffers`. A larger
  buffer cache makes the ledger `SUM` faster, not constant.
- The write-side numbers are one run of each configuration with a synthetic transaction, not the
  capture path itself. Their ratio, not their absolute value, is the finding.
- Warm cache. The JSON also records the cold run of each plan.
- The plans are what the planner chose on this data. A different distribution of accounts can
  change them.
