# v2.0.0 M19 evidence: money-path query plans at one million postings

Synthetic data on one development machine; one warm run per plan. Raw result:
[v2.0.0/money-path-plans.json](v2.0.0/money-path-plans.json). Command:

```bash
uv run python -m scripts.capture_money_path_plans --postings 1000000 \
  --output docs/evidence/v2.0.0/money-path-plans.json
```

The tenant holds 1,000,000 postings, 500,000 journals, 200,000 payments, captures and idempotency
records, 20,000 refunds and 2,000 operations waiting on a lookup. Two ledger accounts carry 98% of
the postings (a hot merchant); a second pair holds 2% (a typical one). Each plan is recorded
freshly loaded and again after `VACUUM`.

| Query (where it runs) | After VACUUM | Plan |
| --- | ---: | --- |
| Payment row lock (`_locked_payment`, every payment command) | 0.04 ms | index scan on `public_id` |
| Idempotency lookup (every command) | 0.01 ms | `idempotency_records_scope_digest_key` |
| Refund trigger: capture lookup | 0.01 ms | `captures_organisation_id_id_key` |
| Refund trigger: reserved sum | 0.03 ms | `ix_refunds_payment_status` |
| Recovery claim (poller, each pass) | 0.18 ms | `ix_provider_operations_recovery` |
| Payments list, first page | 0.07 ms | `ix_payment_intents_organisation_created` |
| Payments list, deep page with status filter | 0.05 ms | same |
| GCRA admit (every API-key request) | 0.04 ms | primary-key upsert |
| Balance sum, typical account (2% of postings) | 1.9 ms | index-only scan, `ix_postings_account_balance` |
| **Balance sum, hot account (98% of postings)** | **320 ms** | **sequential scan of `postings`** |

## The finding

Every plan is an index plan except one: the balance `SUM` for an account that holds nearly all of
the ledger's postings. The planner is right to scan the table. The covering index
`ix_postings_account_balance` would read 980,000 entries, and the table is only slightly larger.
`derive_balances` runs this query three times per call, so a payout, a settlement or a balance read
for such a merchant costs about a second at this size. The cost grows linearly with postings.

This is a limitation, not a defect fixed in v2.0. The balance is derived from the immutable ledger
on every read; it is not a stored running total. A stored balance with a version column exists on
`merchant_accounts` (migration 0029) for optimistic locking, and would be the place to keep a
materialized sum, but doing that changes the ledger's invariants and was not attempted here. It is
recorded in [limitations](../limitations.md).

## Caveats

- One machine, Postgres in Docker with 512 MiB of memory and 128 MB `shared_buffers`. A larger
  buffer cache would make the 320 ms faster, not remove the scan.
- Warm cache. The JSON also records the cold run of each plan.
- The plans are what the planner chose on this data. A different distribution of accounts can
  change them.
