# v2.0.0 M18 evidence: reconciliation at scale

Synthetic data on one development machine. These are measurements of one run, not targets.

## In-database reconciliation of one million lines

Command (raw result: [v2.0.0/reconcile-in-db.json](v2.0.0/reconcile-in-db.json)):

```bash
uv run python -m scripts.reconcile_scale_proof --lines 1000000 \
  --output docs/evidence/v2.0.0/reconcile-in-db.json
```

The proof seeds one tenant with 1,000,000 authorizations (bulk load, triggers disabled for the
fixture only), writes a 91.7 MB provider statement CSV with a known set of exceptions, then runs the
real algorithm-2 path (streamed `COPY` import, chunked matching) in a child process so the memory
figure is the application's, not the script's.

| Measure | Result |
| --- | --- |
| Statement rows | 998,700 (91,658,835 bytes) |
| Streamed import (spool, COPY, validate, insert) | 74.2 s |
| Matching (20 chunks of 50,000 ordinals) | 332.4 s |
| Total | 406.7 s |
| Application peak RSS (child process) | 104.4 MiB |
| Exact matches | 996,800 of 996,800 expected |

Exceptions, seeded against found (the run fails unless every count is equal):

| Type | Seeded | Found |
| --- | ---: | ---: |
| `AMOUNT_MISMATCH` | 1,000 | 1,000 |
| `MISSING_PROVIDER_TRANSACTION` (operation left off the statement) | 2,000 | 2,000 |
| `MISSING_INTERNAL_TRANSACTION` (statement row RelayPay never recorded) | 500 | 500 |
| `DUPLICATE_PROVIDER_EFFECT` (both rows of a repeated key) | 400 | 400 |

Machine: Apple silicon laptop with 8 GiB of memory, macOS, PostgreSQL 17.6 in Docker. The memory
figure excludes the database server. The seeded statement is all `AUTHORIZE` rows, so the join
exercised the authorizations table of the four child tables; `FEE_MISMATCH`, `TAX_MISMATCH` and
`TIMING` are proven by the integration tests, not by this run.

## What the measurement found and fixed

The first runs were 20 to 100 times slower than the final one. Three causes, all found with
`EXPLAIN (ANALYZE)` and fixed before the numbers above:

1. **Stale statistics on a just-imported table.** The application role cannot `ANALYZE`
   `statement_items`, and autovacuum had not reached it, so the planner took it for a one-row table.
   The anti-join for operations missing from the statement became a nested loop of 199 million
   comparisons (34 s for 20,000 rows). Each chunk, and the statement's key list, is now staged in a
   temporary table the session can analyze itself.
2. **An index that hurt foreign keys.** The first draft of migration 0033 indexed
   `provider_operations (organisation_id, environment_id, created_at)`. That shares its prefix with
   every foreign key into the table, so the planner used it for each existence check and scanned a
   whole tenant per row (2.3 ms per check; 47 s for 20,000 matches). The index is now
   `(created_at, organisation_id, environment_id)` and the same insert takes 2.8 s.
3. **A starved disk.** Several early timings were taken with the machine's disk full, which also
   stopped the container runtime. They were discarded.

## Resumability

`tests/integration/test_reconciliation_scale.py` stops a run after one chunk (the state a crashed
worker leaves: `RUNNING`, lease held, `progress_ordinal` advanced) and shows a second pass resumes at
the next ordinal and produces exactly the matches and mismatches of an uninterrupted run. It also
shows a worker holding a stale lease token cannot advance the run.
