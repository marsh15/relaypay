# RelayPay v2.0: "never loses a paisa" (Tally upgrade plan)

## Context

The user shared a rough plan for "Tally", a payments and ledger backend. They asked whether it is relevant to RelayPay and how to bring in its best parts. A full exploration of RelayPay v1.0.1 (142 commits) found that RelayPay already implements Tally's core, in several places more strictly:
- idempotency: route-aware fingerprints, byte-exact replay, 409 on reuse
- lookup-only crash recovery (lost-response handling with no resend)
- a balanced, immutable double-entry ledger with derived balances
- a transactional event plus signed outbound webhooks with dead letter and replay
- a raw inbound inbox with dedupe
- payouts protected by `FOR UPDATE`
- reconciliation with a mismatch workflow
- scoped, rotatable API keys
- OpenTelemetry, Prometheus and Grafana, and strict CI

What RelayPay lacks is Tally's **proof** and **breadth**:
- No property, stateful or chaos testing. Concurrency tests stop at 2 racers, and "crash" tests only simulate a lease expiry.
- No intent state machine, void, auth expiry, partial capture, or fees/GST.
- The provider simulator never pushes webhooks and has no probabilistic chaos.
- Reconciliation runs in memory, capped at 10k rows. There is no seller CSV tool.
- Performance evidence covers only `/health/live`. There is no RCA, runbook, blog post or provenance statement.
- Per-merchant rate limits are missing.

**Outcome:** ship RelayPay **v2.0** across five milestones (M15–M19, one PR plus release evidence each, harness first). It proves that money is never created, lost or moved twice under chaos, with published numbers.

Design calls made in architecture (recommended, verified against code):
- **`/api/v1` stays byte-frozen.** `scripts/check_api_compatibility.py` requires it to be identical to `contracts/openapi/api-v1-v0.6.0.json`. New behaviour goes under `/api/v2` (`apps/api/routes/payments_v2.py`) and calls the same service functions. A new `contracts/openapi/v2.0.0.json` becomes `CURRENT`, and the SDK is regenerated.
- **Status is persisted.** `payment_intents.status` plus `status_version` has one writer, `payments/transitions.py::transition()`. A BEFORE UPDATE trigger enforces the transition table, and the immutable `payment_status_history` table records each change. A `payment_derived_status` view is the oracle the invariants compare against.
- **Webhooks are evidence, not a second money path.**
  - A verified PSP webhook becomes `ProviderAttempt(attempt_kind='WEBHOOK')`, then goes through the existing `finalize_verified_attempt` (`provider_operations/finalizer.py`).
  - The finalizer stays the only code that moves money.
  - Ordering is decided by **state rank**, not sequence numbers, because real PSPs don't give per-intent sequences.
- **Polling fallback is guaranteed.** It reuses the lookup recovery in `provider_operations/recovery.py`. A new `pending_deadline_at` field replaces the 5-lookup review cap for operations awaiting an action, such as UPI collect.
- **Idempotency keys are not purged in v2.0.** `initiate_refund` deduplicates only via the idempotency record unless `merchant_refund_reference` is set, so purging would open a duplicate-refund window. Measure the table's growth and document it.

## Execution model

- **Executors:** Sonnet subagents (`model: "sonnet"`, `effort: "high"`), one per task. Parallel tasks own disjoint files, and each task's owned paths are listed. Only one agent at a time may edit `payments/service.py`, `provider_operations/finalizer.py`, `ledger/service.py` or `apps/worker/poller.py`.
- **Skills:** `incremental-implementation` with `addyosmani-test-driven-development` per task, `code-review-and-quality` per milestone PR, and `verification-before-completion` before calling any milestone done.
- **Branches:** milestone branches are stacked (`v2/m15-proof-harness`, `v2/m16-…`). PRs open as drafts so agents can keep going while the user's files are red.
- **Hand-written gate:**
  - New pytest markers `handwritten`, `proof` and `chaos`.
  - `release-gate` runs `-m "not handwritten and not proof"`. The new `proof-gate` job runs Hypothesis, the concurrency tests and the 20×1000 chaos run. The new `handwritten-gate` job runs `-m handwritten`.
  - A milestone merges only when its user-owned files are green.
- **Upgrade proofs:** every milestone adds `scripts/verify_mN_upgrade.py`, copied from `scripts/verify_m14_upgrade.py`, plus a CI step. Each proof snapshots evidence-table checksums across the upgrade.

## User-owned modules (agents never implement these)

Agents commit the typed interface, a stub that raises `NotImplementedError`, fixtures, and red tests marked `handwritten` and written from the spec. The user implements each one to green. `PROVENANCE.md` lists exactly these files.

1. **Invariant checker** at `packages/relaypay/proof/invariants.py`. Merge gate for M15.
   - Signature: `check_invariants(snapshot: SystemSnapshot, *, quiesced: bool) -> list[Violation]`. Snapshot types live in agent-owned `proof/snapshot_types.py` and `proof/snapshot.py`.
   - Invariants, one code each:
     1. Every journal has at least 2 postings and Σ debit = Σ credit.
     2. Assets = liabilities + income.
     3. Pending, available and receivable are never negative.
     4. Reserved ≤ available.
     5. Refunds ≤ captured.
     6. Captured ≤ authorised.
     7. fee + gst + net = gross, and matches the postings.
     8. At most one provider effect per stable key, and one journal per capture or refund.
     9. No SUCCEEDED resource without a journal, and no orphan journals.
     10. Idempotency bytes equal the operation's terminal bytes.
     11. Status equals the derived view, and the history is a legal walk.
     12. Balance-transaction projection equals the postings.
     13. Provider effects are all known once quiesced.
     14. Every acked op is present.
     15. When quiesced, nothing is non-terminal without a review.
   - Red tests: a golden snapshot returns `[]`, and each single mutation yields exactly its own code.
2. **Payout locking strategies** at `packages/relaypay/payouts/locking/{pessimistic,optimistic,constraint_guard}.py`. Stubs land in M15. They are wired in and benchmarked in M19.
   - `PayoutReserver.reserve(factory, ReserveRequest) -> ReserveOutcome`, with outcomes RESERVED, INSUFFICIENT or REPLAYED, plus attempts.
   - Pessimistic uses `FOR UPDATE` on `merchant_accounts`. Optimistic does a CAS on `balance_version` with bounded retry. The constraint guard relies on the `0022` trigger and maps SQLSTATE 23514 to INSUFFICIENT.
3. **Fee and GST calculator** at `packages/relaypay/fees/calculator.py`, for M16. It is pure and works in integer paise.
   - `compute_capture_fee(amount, terms) -> FeeBreakdown` and `compute_refund_fee_reversal(...) -> FeeReversal`.
   - Fee = half-up(amount × mdr_bps / 10000) + fixed, clamped to the schedule's min and max. GST = half-up(fee × gst_bps / 10000). Net = gross − fee − gst. Raise if net < 0.
   - RETAIN gives a zero reversal. Proportional mode gives the remainder to the final refund.
   - Tests use fixed vectors plus Hypothesis properties.
4. **PSP webhook ordering applier** at `packages/relaypay/psp/ordering.py`, for M17. It is pure.
   - `decide(view: PaymentView, event: NormalizedPspEvent) -> Apply(steps) | Ignore(DUPLICATE|STALE) | Review(reason)`.
   - State rank: created < requires_action < authorised < captured < partially_refunded < refunded. failed, expired and cancelled can only be reached before capture.
   - A skip-ahead event (e.g. captured before authorised) is applied as an implied-predecessor chain.
   - A contradiction (e.g. failed after captured) goes to REVIEW.
   - Refunds are made idempotent by refund id.
   - Red tests: a decision table, plus a fold property over every permutation of a legal event set with each event sent 3 times, which must reach the same final view.

## Risks and traps

- **Capture trigger:** it fires on the finalizer's UPDATE too, so the cancelled, expired and failed guards must be INSERT-only.
- **Capture amount:** `Capture.amount` can now differ from `PaymentIntent.amount`. Grep every consumer, including the console evidence page.
- **Refund dedupe:** refunds are deduplicated only via idempotency, which is why there is no TTL.
- **Connection limits:** the 500-way test needs a compose override for `max_connections` and the pool size.
- **Ledger account fixtures:** many tests hand-create ledger accounts. A zero-fee default must not post fee lines.
- **Adapter fixtures:** Razorpay and Cashfree payload shapes are unverified. The user must confirm the fixtures against test-mode accounts they create themselves.
- **Chaos reproducibility:** thread interleaving is nondeterministic. Always dump the seed schedule.
